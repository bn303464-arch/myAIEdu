# API 명세 생성

백엔드 코드를 읽어 `/api/...` 엔드포인트의 명세를 만든다.

인자: `$ARGUMENTS`

## 원칙

- 코드에서 확인한 내용만 적는다. 확인하지 못한 항목은 지어내지 말고 `확인 필요`로 적는다.
- 만들거나 고치는 파일은 출력 파일 하나다. 예외는 3단계에서 승인받은 `architecture.md` 수정뿐이다.
- 소스 코드와 테스트는 수정하지 않는다. 분석 중 버그를 발견하면 고치지 말고 보고한다.
- 서버를 실행하거나 요청을 보내지 않는다. `app.db`는 열지 않는다. 정적 분석만 한다.
- 예시 값은 가상의 값(`홍길동`, `010-1234-5678`)만 쓴다.
- 문서는 한국어로 쓴다. 경로, 필드 이름, 타입, 오류 메시지는 코드에 있는 그대로 옮긴다.

## 1단계: 출력 경로와 소스 위치 결정

1. 출력 경로는 인자가 있으면 그 값, 없으면 `docs/api.md`다. 프로젝트 밖의 경로, `.md`가 아닌 파일, `src/`·`tests/`·`refactor-proposal/`·`.claude/` 안의 경로는 거절하고 이유를 알린다.
2. 소스 위치(이하 `BACK`)는 프로젝트 루트 기준으로 다음 순서로 정한다.
   - `src/back/routers/`가 있으면 `BACK = src/back`
   - 없고 `refactor-proposal/src/back/routers/`가 있으면 `BACK = refactor-proposal/src/back`. 문서 머리말에 "적용 대기 구조 기준"이라고 표시한다.
   - 둘 다 없으면 파일을 만들지 말고 중단한 뒤 알린다. 루트의 `server.py`·`db.py`(이전 구조)를 대신 분석하지 않는다.

## 2단계: 라우터 분석

파일 이름이나 엔드포인트 목록을 기억에 의존하지 말고 매번 다시 찾는다.

### 2-1. 라우트 수집

1. `BACK/routers/`에서 `router.add(`를 모두 검색한다(Grep). 이 개수가 문서의 엔드포인트 수다.
2. `BACK/server.py`에서 각 라우터의 `register()`가 호출되는지 확인한다. 호출되지 않는 라우터의 경로는 문서에서 빼고 보고한다.
3. 라우트마다 메서드, 경로 정규식, 처리 함수를 기록한다. 정규식의 캡처 그룹은 `{course_id}`처럼 이름 있는 매개변수로 바꿔 표기한다. 이름과 타입은 처리 함수에서 확인한다.

### 2-2. 공통 동작 확인

| 파일 | 확인할 것 |
|---|---|
| `web/router.py` | 경로 비교 방식, 매개변수 추출 |
| `web/handler.py` | 지원 메서드, 예외 → 상태 코드(`ERROR_STATUS`), 일치하는 경로가 없을 때의 응답, 쿼리 문자열 처리, 공통 응답 헤더 |
| `web/messages.py` | 요청 본문을 읽을 때의 오류와 순서, 오류 응답 형식, `Content-Type` |
| `config.py` | 본문 최대 크기 등 요청 제한 |

정적 파일 제공(`web/static_files.py`)은 API가 아니므로 엔드포인트에 넣지 않는다.

### 2-3. 엔드포인트별 추적

각 처리 함수에서 아래 순서로 따라간다. 호출되는 함수는 끝까지 읽는다.

1. **라우터:** 성공 상태 코드, 응답 본문의 모양(객체인지 배열인지), 고정 문구
2. **요청 모델:** 본문이 있으면 `models/`의 `parse()`를 읽는다. 필드별 타입, 필수 여부, 정규화(공백·하이픈 제거, 빈 값 처리), 허용 범위, 상수 값, 오류 메시지를 **검사 순서대로** 적는다. 먼저 실패한 검사의 메시지만 응답된다.
3. **서비스:** `raise`하는 도메인 예외와 발생 조건
4. **저장소:** 호출되는 메서드를 모두 읽는다. 저장소도 도메인 예외를 던진다(예: `sqlite3.IntegrityError`를 변환). 정렬 순서와 계산 필드의 의미는 SQL에서 확인한다.
5. **예외 정의:** `models/errors.py`에서 메시지와 상위 클래스를 확인하고, 상위 클래스를 `ERROR_STATUS`에 대응시켜 상태 코드를 정한다.
6. **응답 필드:** 응답에 쓰는 dataclass의 필드 이름, 순서, 타입 주석을 옮긴다. `str | None`이면 null 가능이다. 타입 주석과 `repositories/schema.sql`이 다르면 둘 다 알린다.

### 2-4. 알려진 제한

- 처리되지 않는 예외, 예상과 다른 형 변환처럼 코드에서 확인되는 문제를 적는다.
- `refactor-proposal/DESIGN.md`나 설계 문서에 기록된 문제는 해당 코드가 아직 그대로인지 확인한 뒤 적고 출처를 밝힌다.

## 3단계: 폴더 승인

`.claude/rules/architecture.md`는 새 최상위 폴더에 승인을 요구한다.

1. 출력 파일의 최상위 폴더가 아직 없거나 `architecture.md`의 디렉터리 절에 없으면, **파일을 쓰기 전에** 사용자에게 만들어도 되는지 묻고 답을 기다린다.
2. 승인되면 디렉터리 절에 그 폴더를 한 줄 추가한다. `tests/test_architecture.py`(또는 `BACK` 옆 `tests/`의 같은 파일)가 최상위 폴더를 검사하지 않으면 테스트는 고칠 것이 없다고 보고한다. 검사한다면 고치기 전에 알린다.
3. 거절되면 파일을 만들지 않고, 분석 결과를 대화에 요약한다.

## 4단계: 문서 작성

- 출력 파일이 이미 있으면 먼저 읽는다. 아래 템플릿에 없는 손으로 쓴 내용이 있으면 덮어쓰기 전에 알리고 확인받는다.
- 아래 템플릿의 제목과 순서를 그대로 쓴다. `{...}`는 실제 값으로 채우고, `<!-- -->` 주석은 결과 문서에 남기지 않는다.
- 해당 없는 항목은 지우지 말고 `없음`이라고 적는다.
- 엔드포인트는 경로 순, 같은 경로는 메서드 순으로 정렬한다.
- 근거는 `파일 경로:줄 번호`로 적는다.

## 5단계: 검증과 보고

작성한 문서를 다시 읽고 확인한다. 어긋나면 고친 뒤 다시 확인한다.

- [ ] 엔드포인트 수가 2-1의 `router.add(` 검색 결과(미등록 라우터 제외)와 같다.
- [ ] 모든 오류 메시지가 `BACK` 안에 같은 문자열로 있다(Grep).
- [ ] 모든 도메인 예외가 하나 이상의 엔드포인트에 연결됐다. 연결되지 않은 예외는 보고한다.
- [ ] 응답 필드의 이름과 순서가 dataclass 또는 라우터 코드와 같다.
- [ ] `{...}` 자리표시자와 `<!-- -->` 주석이 남아 있지 않다. JSON 예시의 중괄호는 정상이다.
- [ ] 개인정보로 보이는 실제 값이 없다.

마지막에 출력 파일 경로, 엔드포인트 수, 이전 문서와 달라진 점, `확인 필요` 항목, 발견한 문제를 짧게 보고한다.
